9.1

Ethical Hacking Fundamentals

DEFINITION
Ethical Hacking is the practice of legally and authorized testing of computer systems, networks and applications to find security vulnerabilities before malicious attackers do — using the same tools, techniques and methodology as real attackers but WITH PERMISSION and for the purpose of improving security. It is also called authorized hacking, white-hat hacking, or security testing. The key difference between ethical hacking and criminal hacking is AUTHORIZATION. Without written permission the same actions are illegal.
RED TEAM
Offensive security team that simulates real-world attacks against an organization to test its defenses. Goes beyond standard pentesting with social engineering, physical access and persistence over extended campaigns. Goal: find weaknesses in people, processes and technology; think like an adversary.
BLUE TEAM
Defensive security team that detects, prevents and responds to attacks — SOC analysts, incident responders, threat hunters and security engineers. Monitors logs, alerts and systems; builds and maintains defenses; responds to red-team findings and real incidents.
info
PURPLE TEAM — Collaborative function where red and blue teams work TOGETHER. Red demonstrates attack techniques while blue simultaneously tests and improves detection and response. The goal is mutual improvement: better detection rules, monitoring and validated defenses.

9.2

Rules of Engagement

WARNING
ALWAYS get written authorization BEFORE any testing. Testing without authorization is a crime regardless of intentions. Even well-intentioned testing without permission can result in criminal charges, civil lawsuits, and damage to careers and organizations.
AUTHORIZATION
The legal foundation of ethical hacking: a signed document explicitly granting permission to test specific systems within defined boundaries. It may be called a scope document, rules of engagement (ROE), penetration testing agreement, authorization to test letter, or statement of work. It must identify the authorizing party/signature authority, in-scope systems, permitted methods, testing timeframe, emergency contacts and data-handling procedures. Without the document in hand, do not test.
SCOPE
Defines what can and cannot be tested: allowed targets, excluded targets, testing window, and permitted/prohibited methods. Going out of scope can end the engagement, void the contract and create legal liability. When in doubt: STOP and ASK the client.
EVIDENCE
Document everything: screenshots, command output, timestamps, methodology notes, affected systems and data. Evidence proves findings and protects the tester by showing exactly what was done and when. Treat accessed data as confidential. Prefer proof-of-concept evidence without exfiltrating real sensitive data.
REPORTING
The deliverable the client pays for. Every finding needs a description, evidence/proof-of-concept, risk rating, business impact and remediation recommendations.
LEGAL & ETHICAL BOUNDARIES
Stay within applicable law (the source references federal/state computer-fraud laws such as CFAA in the US and the IT Act in India), the signed authorization scope and professional ethics. Do not access data beyond what is needed, destroy data, install actual malware, disrupt services beyond authorization or share findings with unauthorized parties. If you accidentally access something out of scope: STOP, document it and notify the client.

Reconnaissance

PHASE 1 — RECONNAISSANCE
PASSIVE RECON
Gather information without directly interacting with target systems: public websites, search engines, social media, DNS records, certificate-transparency logs, WHOIS, job postings, SEC filings and code repositories. No packets are sent to the target and no target-side log entries are generated.
ACTIVE RECON
Direct interaction such as port scanning, DNS zone-transfer attempts, web crawling and banner grabbing. The target may detect it through IDS/IPS and log monitoring. It must be within scope and testing window.

Nmap
# Quick scan common ports
nmap 10.0.0.1

# Full port scan with service versions
nmap -sS -sV -p- 10.0.0.1

# Aggressive full scan
nmap -A -T4 -p- 10.0.0.1

# Specific ports
nmap -p 22,80,443,445,3389 10.0.0.1

# UDP top 100
nmap -sU --top-ports 100 10.0.0.1

# NSE vulnerability scripts
nmap --script vuln 10.0.0.1
nmap --script smb-vuln-ms17-010 10.0.0.1

# Subnet
nmap -sS -sV -p- 10.0.0.0/24

# Save all formats
nmap -sS -sV -p- -oA scan_results 10.0.0.1
NSE
Nmap Scripting Engine categories include vuln, auth, default, discovery and brute. Named examples: http-enum, smb-enum-shares, ssl-heartbleed, dns-brute; categories can be combined such as --script "vuln and safe".
MASSSCAN
Masscan is described as extremely fast and useful for large ranges, followed by Nmap for depth. High rates can disrupt networks and trigger IDS alerts.
VULNERABILITY SCANNERS
Nessus, OpenVAS, Nuclei and Nikto are named. Automated scanners generate false positives; validate every finding manually. They complement, rather than replace, manual testing.

9.7

Vulnerability Assessment

PHASE 4 — VULNERABILITY ANALYSIS
CVE
Common Vulnerabilities and Exposures — standardized naming for publicly known vulnerabilities. Format: CVE-YEAR-NUMBER. The source examples are CVE-2021-44228 (Log4Shell) and CVE-2017-0144 (EternalBlue).
CVSS
Common Vulnerability Scoring System, a 0–10 severity system. Base score reflects intrinsic exploitability/impact; Temporal reflects changes such as exploit/patch availability; Environmental reflects the specific environment. None 0.0, Low 0.1–3.9, Medium 4.0–6.9, High 7.0–8.9, Critical 9.0–10.0.
CWE
Common Weakness Enumeration categorizes types of software weaknesses. Examples in the source: CWE-89 SQL Injection, CWE-79 XSS, CWE-78 OS Command Injection, CWE-22 Path Traversal, CWE-287 Improper Authentication.
EXPLOITABILITY
Consider public exploit availability, authentication requirements, user interaction, required access and whether exploitation is remote or local.
IMPACT
Assess confidentiality, integrity and availability. A remote code-execution vulnerability with root-level impact can affect all three dimensions and must be assessed in business context.

Scanner Accuracy

TypeMeaningWhy It Matters
False PositiveScanner reports a vulnerability that does not actually existMust be manually validated
False NegativeReal vulnerability is missedShows why automated scanning alone is insufficient
VALIDATION & PRIORITIZATION
Validate exact software versions, reproduce the issue, check patches/mitigations and understand exploitation conditions. Prioritize using CVSS, exploitability, exposure, business impact and attack surface; a practical model is Likelihood × Impact.
9.8

Exploitation Fundamentals

PHASE 5 — EXPLOITATION
TECHNIQUE
Exploitation should ONLY be performed against systems within authorized scope using approved methods.
EXPLOIT
A piece of code, technique or sequence of commands that takes advantage of a vulnerability to produce an unintended or unauthorized effect. Types named: remote, local, client-side and web exploits.
PAYLOAD
Code that runs after successful exploitation. The exploit is the delivery mechanism; the payload performs the useful action. Types named: reverse shell, bind shell, command execution, file transfer and Meterpreter.
REVERSE SHELL
Target initiates an outbound connection to the tester's listener. Often works better where inbound connections are restricted.
BIND SHELL
Target opens a listening port and the tester connects inbound. Simpler conceptually but often blocked by firewalls.

METASPLOIT
Metasploit Framework includes exploit modules, payloads, auxiliary scanners/fuzzers/brute-forcers, post-exploitation modules and encoders. The source names TryHackMe Metasploit rooms and Metasploit Unleashed as learning resources.
EXPLOIT CHAINS
Multiple vulnerabilities can combine so that each enables the next: information disclosure → vulnerable version/CVE → limited access → local privilege escalation → credential discovery → lateral movement. Professional pentests look for chains because they demonstrate realistic attack paths and maximum impact.
9.9

Password Attacks

BRUTE FORCE
Systematically tries every possible combination. Online attacks are constrained by network speed, rate limiting and lockout; offline attacks are constrained primarily by computing power and hash strength.
DICTIONARY
Tries likely passwords from wordlists such as rockyou.txt and SecLists. Hydra is named for online attacks; Hashcat and John for offline hashes.
PASSWORD SPRAYING
Tries a small number of common passwords across many accounts, reducing per-account failures and often avoiding lockouts.
CREDENTIAL STUFFING
Uses username/password pairs from previous breaches against other services, exploiting password reuse.
PASSWORD HASHES
Passwords should not be stored in plaintext. Systems store hashes; login hashes the entered password and compares the result. Hashes can still be attacked by guessing.
SALTING
Adds a unique random string before hashing, defeating precomputed rainbow tables and forcing separate cracking work for each password.

Hashcat / John Examples

Hashcat / John
# Hashcat: NTLM
hashcat -m 1000 -a 0 hashes.txt rockyou.txt

# Hashcat: MD5 with rules
hashcat -m 0 -a 0 hashes.txt rockyou.txt -r rules/best64.rule

# John
john --wordlist=rockyou.txt hashes.txt
john --show hashes.txt
