Web Technologies

Module 5 — Internet, web protocols, application architecture, APIs, authentication, sessions and web security.

5.1 Internet & Web

Internet: The Internet is a global network of interconnected networks using TCP/IP. It consists of physical infrastructure such as cables, routers, switches and servers spanning the globe. It is not owned by one entity; it is a collaboration among ISPs, governments and organizations.
World Wide Web: The WWW is a service that runs on top of the Internet: a system of interlinked hypertext documents accessed primarily through HTTP and browsers. Tim Berners-Lee invented the Web in 1989. The Web is not the Internet; email and FTP are other applications that use the same Internet infrastructure.
Client
A device or software that requests resources. Examples: browser, mobile app, Python HTTP script.
Server
Device or software that provides resources in response to requests and waits for connections.
Browser
Client application that requests HTML/CSS/JS, parses it and renders pages. DevTools expose Network, Console, Elements and Application views.
Web Server
Handles HTTP requests and serves static content. Apache, Nginx and IIS commonly listen on ports 80 and 443.
Application Server
Runs dynamic business logic using platforms such as Django, Flask, Express, Spring or Tomcat.
Database Server
Stores and manages application data. MySQL, PostgreSQL, MongoDB, SQLite and Oracle are examples; databases should not be directly internet-exposed.
CDN: A Content Delivery Network uses geographically distributed edge servers to cache static resources such as images, CSS and JavaScript close to users, reducing latency and origin load. Cloudflare, Akamai and AWS CloudFront are examples. CDNs can also provide DDoS protection and WAF capabilities.
Proxy: An intermediary between a client and server. A forward proxy sits in front of clients and can hide client IPs, cache, filter and log activity. A reverse proxy sits in front of servers and can load-balance, terminate TLS, cache, compress, protect infrastructure and hide backend servers. Nginx, HAProxy and Cloudflare can perform reverse-proxy functions.

5.2 URL

URL (Uniform Resource Locator): The address of a resource on the Web. It tells the browser where a resource is and how to retrieve it.
Scheme
http:// is unencrypted; https:// uses TLS. Other schemes include FTP and SSH.
Host
The server name or IP. A domain may be resolved through DNS.
Port
The server's logical door. Defaults: 80 HTTP, 443 HTTPS; custom ports such as localhost:8080 are explicit.
Path
Hierarchical resource or endpoint, such as /products/search.
Query
Key-value pairs after ?, separated by &. They are visible in history and logs, so never put passwords or sensitive data there.
Fragment
Part after #. It is normally not sent to the server and can support client-side navigation.
URL encoding and security: Reserved/special characters can be percent-encoded as %XX: space %20 or +, & %26, = %3D, / %2F, < %3C, > %3E, " %22. Attackers may use encoding, double encoding such as %2527, or mixed encodings to evade weak filters.

5.3 HTTP

HTTP (HyperText Transfer Protocol): An application-layer protocol that defines how clients request resources/actions and servers respond. HTTP is stateless: each request is independent unless an application adds state through mechanisms such as sessions and cookies. HTTP messages are designed to be readable textually.

Request

A request contains a method, path/target, HTTP version, headers and an optional body.

GET /api/users?role=admin HTTP/1.1 Host: example.com User-Agent: Mozilla/5.0 Accept: application/json Cookie: session=abc123 Authorization: Bearer eyJhbG...

Response

A response contains the HTTP version, status code/reason phrase, headers and an optional body.

HTTP/1.1 200 OK Content-Type: application/json Set-Cookie: session=abc123; HttpOnly; Secure Content-Length: 245 {"users": [{"id": 1, "name": "alice", "role": "admin"}]}

TLS: Transport Layer Security is a cryptographic protocol providing encryption, authentication and integrity for network communications. TLS 1.3 is the current modern version. SSL (Secure Sockets Layer) is the predecessor; SSL 2.0 and 3.0 are obsolete and insecure. The phrase “SSL certificate” commonly refers to a TLS certificate.
Certificate: An X.509 digital document containing information such as the server/domain identity, public key, issuer, validity dates and the issuer's digital signature. A browser validates it to establish that it is communicating with the intended server.
Certificate Authority: A trusted CA issues certificates. The browser trusts a built-in set of root CAs. A typical chain is Root CA → Intermediate CA → Server Certificate. Examples of certificate authorities include Let's Encrypt, DigiCert and Comodo.
Public Key
Included in the certificate. Used in public-key cryptography and signature verification.
Private Key
Secret server-side key. It must never be shared; compromise can allow server impersonation and undermine connection security.

TLS Handshake

1Client Hello
Supported TLS versions, cipher suites and random material.
2Server Hello
Chosen parameters plus the server certificate.
3Certificate Verification
Browser checks trust chain, hostname, validity and applicable revocation status.
4Key Exchange
TLS 1.3 uses ephemeral Diffie-Hellman key exchange to establish shared keying material.
5Secure Connection
Subsequent application data uses fast symmetric cryptography.
Certificate validation: Browsers check CA trust, hostname matching, expiration and applicable revocation information. A failure can trigger a “Your connection is not private” warning. Do not click through certificate warnings. HTTPS protects traffic in transit; it does not make an insecure application automatically secure.

5.5 HTML

HTML: HyperText Markup Language is the standard markup language for creating web pages. It describes structure and content using elements and tags. HTML is not a programming language.
Elements, tags and attributes: An element can have an opening tag, content and closing tag, e.g. <p>Hello world</p>. Some elements such as <br>, <img> and <input> do not require a closing tag. Attributes add information, e.g. <a href="https://example.com" target="_blank">Link</a>.

Forms, Inputs, Links and Images

Forms collect user input and submit it to a server. <form action="/login" method="POST"> defines destination and method. Inputs include text, password, email, number, file, hidden, checkbox, radio and submit. Links use <a href="URL">; images use <img src="URL" alt="description">.

Security relevance: Forms are major attack surfaces. Never trust hidden inputs such as <input type="hidden" name="admin" value="false">; users can modify them in DevTools. File uploads require strict validation and safe storage. Event-handler attributes such as onclick, onload and onerror can become XSS vectors. User-controlled links can enable open redirects. External images can also be abused for tracking or data exfiltration; an onerror handler can be an XSS vector.

DOM

DOM (Document Object Model): The browser's object-tree representation of an HTML document. JavaScript can read and modify DOM nodes using methods such as document.getElementById() and document.querySelector(). DOM-based XSS can occur when attacker-controlled sources such as location.hash, location.search or document.referrer reach dangerous sinks such as innerHTML, document.write() or eval().
HTML encoding: Encode special characters before inserting untrusted data into HTML. Characters such as <, >, &, quotes and apostrophes have HTML-safe representations. Correct context-specific encoding turns injected markup into data rather than executable markup.

5.6 CSS

CSS: Cascading Style Sheets controls visual presentation: colors, fonts, spacing, layout and animation. HTML provides structure; CSS provides style.

Selectors and Properties

Selectors target elements: p {}, .classname {}, #id {}, input[type="password"] {}, div p {} and pseudo-classes such as a:hover {}. Properties include color, font-size, background-color, border, padding, margin, display and position.

CSS security: CSS is not normally a security boundary, but security testers should understand CSS injection, UI redressing/clickjacking and CSS-based data exfiltration. For example, carefully crafted attribute selectors can sometimes infer characters in input values by causing network requests.

Layout and Responsive Design

The box model consists of content + padding + border + margin. Common display systems are block, inline, flex and grid; positioning includes static, relative, absolute, fixed and sticky. Responsive design uses fluid sizing, viewport configuration and media queries such as @media (max-width: 768px).

5.7 JavaScript (Web Security Context)

Client-side JavaScript: JavaScript delivered to and executed by the browser. Users can inspect and modify it, so client-side validation and security logic cannot be trusted. Never place secrets or security decisions solely in client-side code.

DOM Manipulation and Events

document.getElementById("output").innerHTML = userInput;

If userInput is untrusted HTML, assigning it to innerHTML can create DOM-based XSS. Prefer textContent when inserting plain text. Events include click, submit, keypress, load, error, mouseover, focus and blur; event listeners can be registered with addEventListener().

Event-handler security: HTML event attributes such as <body onload="malicious()"> and <img onerror="malicious()"> are dangerous XSS sinks when attacker-controlled content reaches them.

Cookies, Local Storage and Session Storage

document.cookie
Reads non-HttpOnly cookies and can set cookies. XSS can abuse readable cookies, which is why HttpOnly is important.
localStorage
Key-value storage with no automatic expiration. It is not sent with HTTP requests and is readable by JavaScript on the same origin.
sessionStorage
Similar API but scoped to a browser tab/session. It remains readable by same-origin JavaScript and therefore is not safe for secrets against XSS.
document.cookie = "name=value; path=/; secure"; localStorage.setItem("key","value"); sessionStorage.setItem("key","value");

Fetch API and AJAX

fetch("https://api.example.com/data", { method: "GET", headers: {"Authorization": "Bearer token"} }).then(r => r.json()).then(data => console.log(data));

Fetch is the modern browser API for HTTP requests and supports methods, headers and request bodies. AJAX means making asynchronous HTTP requests without a full page reload; modern applications generally use Fetch rather than the older XMLHttpRequest. Cross-origin requests are constrained by browser security and CORS.

Same-Origin Policy

SOP: The Same-Origin Policy restricts how scripts from one origin interact with another. An origin is scheme + host + port, so https://example.com:443 and http://example.com:80 are different origins. SOP is enforced by browsers and prevents cross-origin DOM access and reading protected cross-origin responses. XSS is dangerous because injected JavaScript executes in the victim origin and therefore operates within that origin's privileges.

5.8 Web Sessions

Session: A mechanism that maintains state across multiple HTTP requests. Because HTTP is stateless, applications use sessions so the server can remember an authenticated user across requests.
Session ID: A unique, random and unpredictable identifier associated with server-side session data. If an attacker guesses or steals it, they may impersonate the user.
Cookies: Small browser-stored data sent with requests to a matching domain/path. Set-Cookie creates them; Cookie sends them. Attributes include Domain, Path, Expires/Max-Age, Secure, HttpOnly and SameSite.
Session cookie
No Expires/Max-Age; generally removed when the browser closes.
Persistent cookie
Has Expires/Max-Age and can survive browser restarts; useful for remember-me features but increases exposure window.
Session expiration
Idle timeout ends after inactivity; absolute timeout ends after a maximum lifetime.
Session fixation: An attacker causes a victim to use a known session ID before authentication. Regenerate the session ID after login.

Session hijacking: An attacker steals a valid session ID through XSS, insecure transport or other means. Use HTTPS and Secure/HttpOnly cookie protections.

Session prediction: Weak predictable IDs can be guessed. Use cryptographically random identifiers of sufficient length.

5.9 Authentication

Authentication: The process of verifying a user's identity. Login is a major attack surface because credentials can be targeted by brute force, dictionaries, credential stuffing and password spraying.
Passwords: Store passwords as salted, adaptive password hashes rather than plaintext or reversible encryption. Algorithms such as Argon2, scrypt and bcrypt are designed for password hashing. Defenses include rate limiting, MFA, strong password practices and detection of credential abuse.

MFA and OTP

MFA requires two or more different factors: something you know, something you have, or something you are. TOTP generates time-based codes in authenticator applications; HOTP uses a counter. SMS OTP is weaker because SIM-swap attacks can compromise the phone number, although it can still be better than password-only authentication.

Authentication Tokens

After login, an application may issue an opaque or structured token that the client presents on subsequent requests. Tokens may be carried in an Authorization header or protected cookie.

SessionsTokens
Server stores session state; client holds a session ID.Often self-contained; server can validate token integrity without a per-session lookup.
Traditional stateful model.Common in APIs and SPAs.

JWT

JSON Web Token: A compact token with three Base64URL-encoded parts separated by dots: Header.Payload.Signature. The header describes the algorithm/type; payload contains claims; signature provides integrity/authenticity when correctly verified.
Header: {"alg":"HS256","typ":"JWT"} Payload: {"sub":"user123","name":"alice","role":"admin","exp":1234567890} Token: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c2VyMTIzIiwibmFtZSI6ImFsaWNlIiwicm9sZSI6ImFkbWluIn0.SIGNATURE
JWT security: Base64URL encoding is not encryption, so payloads are readable. Do not place passwords or secrets in them. Validate the expected algorithm and signature correctly; algorithm-confusion/“none” mistakes and weak HMAC secrets can undermine verification. JWTs also require deliberate expiry/revocation design because a valid issued token may remain usable until it expires or is otherwise invalidated.

OAuth 2.0

OAuth 2.0: An authorization framework that lets a user grant a third-party application limited access without sharing the user's password with that application. “Sign in with Google” commonly involves related authorization and identity technologies; OAuth itself is authorization, not authentication.
1User starts login
App redirects to authorization server.
2Consent
User authenticates and grants requested permissions.
3Authorization code
Authorization server redirects back with a code.
4Token exchange
App exchanges the code at the token endpoint.
5Resource access
App uses access token for permitted resources.
Grant types: Authorization Code is the modern general-purpose flow; Implicit is legacy and deprecated for modern applications; Client Credentials is for machine-to-machine access; Resource Owner Password Credentials is legacy and should not be used in new designs.

OIDC and SSO

OpenID Connect (OIDC) adds an authentication/identity layer on top of OAuth 2.0 and can return an ID token containing identity claims. Single Sign-On (SSO) lets a user authenticate once and access multiple applications. Enterprise deployments commonly use SAML or OIDC. SSO reduces repeated password entry but makes the central identity account especially important to protect.

5.10 Web Architecture

Client
Sends requests, renders responses and executes client-side JavaScript. XSS can abuse its origin privileges.
Web Server
Serves static files and proxies dynamic requests. Harden configuration, disable unnecessary modules/directory listing and patch software.
Application Server
Runs business logic, authentication and data processing. Common vulnerability classes include SQL injection, command injection, SSRF and logic flaws.
Database
Stores persistent data. Avoid direct internet exposure, use least-privileged accounts and parameterized queries.

API, Microservices, Load Balancing, Reverse Proxy, CDN and WAF

An API defines how software components communicate, commonly using HTTP and JSON. Microservices split an application into independently deployable services, such as user, payment and notification services, increasing flexibility but also the number of security boundaries.

A load balancer distributes traffic across backends using methods such as round robin, least connections or IP hash. It can operate at Layer 4 or Layer 7 and supports high availability. A reverse proxy can terminate TLS, cache, compress and centralize logging/access control. A CDN caches content at the edge. A WAF inspects HTTP traffic and can block patterns associated with SQL injection, XSS, path traversal, command injection and malicious uploads.

WAF limitation: A WAF is defense in depth, not a replacement for secure coding. Encoding tricks, obfuscation and novel attack patterns can bypass rule-based defenses.

5.11 APIs

API: An Application Programming Interface is a defined set of rules and protocols for software components to communicate. Web APIs commonly expose HTTP endpoints and return structured data such as JSON. Frontends, mobile applications, backend services and third-party integrations depend on APIs.

REST and SOAP

REST: Representational State Transfer is a dominant architectural style for web APIs. REST APIs are commonly stateless, resource-oriented and use standard HTTP methods with JSON representations.
GET /api/users GET /api/users/123 POST /api/users PUT /api/users/123 DELETE /api/users/123
SOAP: Simple Object Access Protocol is an older XML-based web-service protocol with strict standards such as WSDL. It remains common in enterprise, banking and government legacy systems and has WS-Security for message-level security.

JSON and XML

{ "name": "alice", "age": 25, "roles": ["admin", "user"], "active": true }

JSON supports objects, arrays, strings, numbers, booleans and null. XML uses tags, for example <user><name>alice</name><age>25</age></user>. XML parsers must be configured safely because XXE can expose local files, enable SSRF or cause denial of service.

REST Methods with Bodies

POST /api/users HTTP/1.1 Host: api.example.com Content-Type: application/json Authorization: Bearer eyJhbG... {"name":"alice","role":"user"}
PUT /api/users/123 HTTP/1.1 Host: api.example.com Content-Type: application/json Authorization: Bearer eyJhbG... {"name":"alice","role":"admin","active":true}

Rate Limiting

Rate limiting: Restricts request volume per time window, such as 100 requests/minute. Limits can be based on IP, API key or user. Excess requests commonly receive 429 Too Many Requests, optionally with Retry-After. Rate limiting helps resist brute force, scraping, abuse and resource exhaustion.
API Security Checklist:
  1. Always use HTTPS.
  2. Authenticate every protected request.
  3. Authorize every sensitive action.
  4. Validate all input server-side.
  5. Rate limit all endpoints, especially login.
  6. Return only necessary data.
  7. Use parameterized database queries.
  8. Log requests for security monitoring.
  9. Version APIs such as /api/v1/ so insecure versions can be deprecated.
  10. Use the OWASP API Security Top 10 as a comprehensive reference.

5.12 Web Security Concepts

Same-Origin Policy: A fundamental browser security mechanism based on scheme + host + port. It restricts scripts from reading/interacting with data across origins. SOP does not stop every cross-origin request: browsers can load resources such as images, scripts and styles, and forms can submit cross-origin requests; the key protection is restricting cross-origin access to protected data and DOMs.

CORS

Cross-Origin Resource Sharing: A controlled mechanism for relaxing SOP. The server uses response headers to tell the browser which origins may read responses.
Access-Control-Allow-Origin: https://trusted-app.com Access-Control-Allow-Methods: GET, POST Access-Control-Allow-Headers: Authorization, Content-Type Access-Control-Allow-Credentials: true

For non-simple cross-origin requests, the browser can send an OPTIONS preflight before the actual request. Access-Control-Allow-Origin: * permits all origins and is inappropriate for many sensitive endpoints. Reflecting arbitrary Origin values while allowing credentials can expose authenticated responses to attacker-controlled sites.

CSRF

Cross-Site Request Forgery: An attack that causes a logged-in user's browser to submit an unwanted request to a site where the user is authenticated. Browsers may automatically attach cookies to the target site's request.
CSRF defenses: anti-CSRF tokens verified server-side, appropriate SameSite cookies, checking Origin/Referer where suitable, and re-authentication for especially sensitive actions.

CSP

Content Security Policy: An HTTP response policy that restricts which sources the browser may load or execute for scripts, styles, images, frames and other content. It is an important defense-in-depth control against XSS.
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.example.com; style-src 'self' 'unsafe-inline'; img-src *

A strict policy can prevent unauthorized scripts from executing even when an injection flaw exists. 'unsafe-inline' weakens script/style restrictions, while 'unsafe-eval' permits dangerous dynamic evaluation and should be avoided where possible. CSP violation reporting can support monitoring.

Input Validation

Input validation: Check that input matches the expected type, length, range, format and allowed characters before processing. Prefer allowlists over blocklists. Validation must happen server-side because client-side checks can be bypassed. Validation reduces risk from SQL injection, XSS, command injection, path traversal and other injection classes.

Output Encoding

Output encoding: Transform untrusted data into a safe representation before inserting it into a specific output context. HTML, URL, JavaScript and CSS contexts require different encoding rules. Proper contextual encoding makes data remain data rather than executable code.
User input: <script>alert(1)</script> Safely HTML-encoded output: &lt;script&gt;alert(1)&lt;/script&gt;
Web Security Defense Layers:
  1. Input Validation — reject bad data at the boundary.
  2. Output Encoding — neutralize data before rendering.
  3. Parameterized Queries — prevent SQL injection.
  4. CSRF Tokens — prevent forged state-changing requests.
  5. CSP Headers — restrict executable content.
  6. Cookie Flags — Secure, HttpOnly and SameSite for authentication cookies.
  7. HTTPS Everywhere — encrypt traffic in transit.
  8. CORS Configuration — restrict cross-origin response access.
  9. Rate Limiting — reduce brute force and abuse.
  10. Security Headers — including X-Frame-Options, X-Content-Type-Options, Referrer-Policy and Permissions-Policy.
Principle: These controls work together as defense in depth; no single control is sufficient for a secure web application.
